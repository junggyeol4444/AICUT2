Broadcast-to-YouTube Autonomous Content Producer

문서 버전: 통합 v1 · 작성 기준일: 2026-08-19

> 이 파일은 사용자가 제공한 기획안 원문이다. 구현의 유일한 근거 문서이므로
> 내용을 임의로 요약하거나 수정하지 않는다. 각 장이 코드 어디에 구현되어

## [문서 통합 관계]

- 상위 기획 골격: ai편집.txt
- 기획 배경 및 호흡(페이싱) 개념: 재미나이 v1에서 흡수
- 구현 명세(DB / 상태머신 / 예외처리 / 기술스택 / UI): 재미나이 v2에서 흡수 후 수정
- 재미나이 v2의 고정 임계값(-40dB, 0.3초, 0.7 등)은 근거 데이터가 없어 전량 제거하고,
  17장의 캘리브레이션 절차로 대체함

1. 에피소드를 원본의 연속 구간(start_sec ~ end_sec)으로 고정한 v2 스키마를 폐기하고,
   컷 단위 타임라인 구조로 교체 → 비선형 재구성 가능
2. 자막 스타일 고정값(폰트/크기/색상)을 참조 파라미터로 강등

4. acrossfade 오용 수정
5. YouTube API 쿼터 관련 사실관계 수정
6. 화자분리 모델 사전 승인 절차 명시
7. 3종 학습 루프(레퍼런스 / 원본↔완성본 / 성과)를 상위 구조로 복원
8. 사람 검수 게이트를 파이프라인 정식 단계로 승격

## 1. 프로젝트 개요

### 1.1 프로젝트 한 줄 정의

긴 생방송 영상 하나를 AI가 전체적으로 이해하고, 현재 YouTube에서 실제로 제작되고 있는
영상들의 구성, 편집, 스토리텔링, 장면 선택, 제목, 썸네일 및 시청자 반응을 분석하여
제작 지식을 확보한 뒤, 생방송 안에서 독립적으로 콘텐츠가 될 수 있는 내용을 스스로
발견하고, 콘텐츠의 개수와 종류, 필요한 원본 장면, 영상의 구성 방식, 편집 방법까지
스스로 결정하여 여러 개의 YouTube 영상을 제작하는 시스템.

### 1.2 기획 배경 (기존 AI 편집기의 한계)

현재 시장의 자동 편집 도구(Vrew, Opus Clip 계열)는 상용 채널의 메인 편집기로 쓸 수 없다.
이유는 세 가지다.

1. **맥락 없는 짜깁기** — 데시벨이 높거나 특정 키워드가 등장한 구간만 긁어모아
   기승전결도 주제도 없는 결과물을 만든다.
2. **호흡의 파괴** — 오디오 갭 킬링을 기계적으로 적용해 짧은 무음도 일괄 삭제한다.
   이로 인해 황당해하는 표정, 대답 직전의 정적 등 예능에서 가장 중요한 '마'가 사라진다.
3. **시각적 인지 부재** — 화면이 토크인지 게임인지 다인원 합방인지 구분하지 못하고
   오직 음성에만 의존해 컷을 넘긴다.

본 프로젝트는 이 세 가지를 해결하되, "좋은 장면을 찾는 것"이 아니라
"방송에서 어떤 콘텐츠가 존재하는지 이해하는 것"을 목표로 한다.

### 1.3 목표

사용자가 4~10시간 분량의 생방송 영상 하나를 입력하면 AI가 방송 전체를 분석하고,
의미 있는 콘텐츠를 스스로 찾아내 독립된 YouTube 영상 N개를 제작한다.

결과 예시:

```
생방송 1개 → 장편 4개 + Shorts 5개
생방송 1개 → 장편 2개 + Shorts 3개
생방송 1개 → 장편 1개
생방송 1개 → 제작 가치가 있는 콘텐츠 없음
```

마지막 케이스(0개 출력)도 정상 결과로 인정한다.

### 1.4 기존 자동 편집 시스템과의 차이

일반적인 자동 편집:
긴 영상 → 재미있는 장면 탐색 → 장면 추출 → 클립 생성

본 프로젝트:
긴 생방송 → 방송 전체 이해 → 사건과 흐름 파악 → 서로 연결된 장면 파악 →
독립 콘텐츠 후보 발견 → 콘텐츠별 가치 판단 → YouTube 제작 패턴 참고 →
콘텐츠별 제작 전략 결정 → 필요한 장면 검색 → 원본 장면 재구성 → 자동 편집 →
완성 영상 제작 → 성과 분석 → 재학습

## 2. 설계 철학 (하드코딩 금지 원칙)

### 2.1 영상 구조를 하드코딩하지 않는다

`Hook → Context → Conflict → Climax → Resolution`

위 구조를 시스템 고정 규칙으로 쓰지 않는다. 하나의 콘텐츠에는 맞을 수 있으나
모든 영상에 맞는 구조는 아니다. AI가 콘텐츠 특성을 분석해 구조를 스스로 결정한다.

### 2.2 콘텐츠 개수를 하드코딩하지 않는다

"방송 하나당 무조건 3개" 같은 규칙을 쓰지 않는다. 0개도 허용한다.

### 2.3 콘텐츠 종류를 하드코딩하지 않는다

게임 / 토크 / 합방 / 사건 같은 분류를 출력의 고정 카테고리로 사용하지 않는다.
이 라벨들은 내부 분석 신호로만 쓰고 출력 규격으로 승격시키지 않는다.

### 2.4 시간순 편집을 강제하지 않는다

원본의 시간 순서는 데이터일 뿐이다. 필요하면 서로 다른 시간대의 장면을 연결한다.

예: `05:12:31 → 01:42:10 → 03:21:42 → 05:13:10`

단순히 순서를 섞는 것이 아니라 시청자가 내용을 이해할 수 있도록 맥락을 유지해야 한다.

> 이 원칙 때문에 데이터 모델이 결정된다. 에피소드를 원본의 연속 구간 하나로 저장하면
> 이 원칙이 불가능해진다. 13장 참조.

### 2.5 화면이 아니라 사건으로 나눈다

토크 / 게임 / 합방은 화면의 상태일 뿐 콘텐츠의 경계가 아니다.
하나의 영상은 하나의 사건으로 완결되어야 하며, 화면 상황이 바뀐다는 이유로
나누거나 붙이지 않는다. 상세는 6.2 참조.

### 2.6 영상 길이를 하드코딩하지 않는다

목표 길이 슬라이더는 사용자 힌트로만 취급한다. AI가 콘텐츠에 맞는 길이를 결정하며,
힌트와 어긋나면 그 사유를 리포트에 남긴다.

## 4. 핵심 시스템 1 — YouTube Content Intelligence

목표: 현재 YouTube에서 실제로 제작되는 영상들을 분석해
"좋은 콘텐츠가 어떤 방식으로 만들어지는지" 제작 패턴을 확보한다.

### 4.1 수집 범위

처음부터 YouTube 전체를 분석하지 않는다. 제작하려는 콘텐츠와 관련성이 높은 분야부터
좁게 시작한다.

게임 스트리머 / 인터넷 방송 / 생방송 편집 영상 / 게임 하이라이트 / 합방 /
리액션 / 토크 / 예능형 콘텐츠

### 4.2 수집 대상

영상, 제목, 썸네일, 설명, 업로드 날짜, 영상 길이, 조회수, 좋아요, 댓글, 채널, 카테고리

> **사실관계 주의**
> 평균 시청 지속 시간, 시청자 유지율, 이탈 구간, 재시청 구간, 클릭률은
> YouTube Analytics API를 통해 "본인 소유 채널"에서만 조회 가능하다.
> 타 채널 영상에서는 공개 지표(조회수/좋아요/댓글 수) 수준까지만 얻을 수 있다.
> 따라서 레퍼런스 학습(4장)은 공개 지표 기반으로 설계하고,
> 유지율 기반 학습은 12장(성과 학습, 자기 채널 한정)에서만 다룬다.

### 4.3 영상 자체 분석 항목

- **영상 구조**: 시작 방식 / 정보 공개 순서 / 사건 진행 / 장면 연결 / 결말 / 종료 방식
- **편집**: 컷 / 평균 장면 길이 / 확대 / 크롭 / 화면 전환 / 자막 / 강조 / 효과 /
  효과음 / BGM / 이미지 / 밈 / 리플레이
- **스토리텔링**: 어떤 정보를 먼저 보여주는가 / 어떤 정보를 늦게 공개하는가 /
  어떤 장면을 생략하는가 / 어떤 장면을 반복하는가 /
  서로 다른 시간대의 장면을 어떻게 연결하는가
- **인물**: 누가 중심 인물인가 / 누구의 반응이 중요한가 / 관계 표현 방식

### 4.4 제작 논리 추출

"자막이 많다", "컷이 빠르다" 수준에서 멈추지 않고 "왜 이렇게 편집했는가"까지 분석한다.

예: 사건 발생 → 결과 장면을 먼저 노출 → 궁금증 유도 → 과거 장면으로 이동 →
원인 설명 → 사건 진행 → 결과

이것을 하나의 제작 패턴으로 추출한다.

### 4.5 YouTube Content Knowledge

콘텐츠 구성 패턴 / 편집 패턴 / 스토리텔링 패턴 / 장면 선택 패턴 / 영상 템포 /
자막 사용 패턴 / 반응 강조 방식 / 제목 패턴 / 썸네일 패턴 / 영상 길이와 구성의 관계

이 지식을 고정 규칙으로 만들지 않는다. 새 방송을 제작할 때 참고하는 지식으로만 쓴다.

### 4.6 학습과 복제의 구분

특정 영상 하나를 그대로 복제하는 것이 목적이 아니다.

```
Reference A / B / C / D
        ↓
   공통 제작 패턴 분석
        ↓
   YouTube 제작 지식
        ↓
   새로운 생방송에 적용
```

> **법적 주의**
> 레퍼런스 영상의 원본 파일을 대량 다운로드·보관하는 방식은 YouTube 서비스 약관 및
> 저작권 문제 소지가 있다. 본 시스템은 분석 결과(수치·패턴·메타데이터)만 저장하고
> 원본 미디어는 분석 후 폐기하는 것을 기본 정책으로 한다.
> 이 정책은 MVP 1 착수 전에 확정해야 한다.

## 5. 핵심 시스템 2 — Long-Term Broadcast Understanding

### 5.1 스캔 방식 — 2단계 통과

사람 편집자는 원본을 처음부터 끝까지 다 본다. 배속으로 훑다가 뭔가 있으면 정속으로
되돌려 다시 본다. 이 시스템도 같은 방식으로 원본을 통과한다.

**[1차 통과 — 전 구간 훑기]**
방송 처음부터 끝까지 빠짐없이 통과한다. 화면 전환이 없는 구간도 건너뛰지 않는다.
(게임 화면이 30분간 그대로여도 그 안에서 일이 벌어진다)

```
이 단계에서 파악하는 것:
  지금 무슨 상황인가 / 누가 있는가 / 무슨 얘기가 오가는가 /
  화면에서 무슨 일이 벌어지는가 / 어디가 다시 볼 만한가

출력: 구간별 요약 + 정밀 확인이 필요한 지점 표시
```

**[2차 통과 — 표시된 구간만 정밀하게]**
1차에서 표시된 구간만 촘촘하게 다시 본다.

```
이 단계에서 파악하는 것:
  정확히 언제 시작하고 끝나는가 / 대사와 반응의 정확한 타이밍 /
  표정과 동작 / 편집에 필요한 세부 정보

출력: 정밀 구간 데이터
```

1차는 넓고 성기게, 2차는 좁고 촘촘하게 간다.
1차의 통과 밀도와 2차 대상 선정 기준은 17장에서 측정한다.

> 화면 전환 감지로 1차 통과를 대체하지 않는다.
> 전환이 없는 구간에도 내용은 계속 존재한다.

### 5.2 통과 시 함께 보는 것

1차·2차 모두 화면과 소리를 분리하지 않고 같이 본다.

- **화면**: 인물 / 표정 / 동작 / 게임 상황 / 게임 결과 / 채팅·후원 / 화면 사건
- **음성**: 발화 내용 / 대화 흐름 / 말투 / 감정 / 중요 발언
- **오디오**: 웃음 / 비명 / 환호 / 침묵 / 효과음 / BGM 변화

> 오디오는 멀티트랙 원본을 전제로 한다(20장). 내 마이크 / 통화 / 게임 / BGM 트랙이
> 분리되어 있으므로 혼합 오디오에서 화자를 추출하는 과정이 필요 없다.
> 통화 트랙에 2인 이상이 있는 경우에만 트랙 내 화자 구분을 적용한다.

모든 정보에 타임스탬프를 연결한다.

### 5.3 상황 라벨

통과 중 화면 상황을 구간 단위로 기록한다. 내부 분석 신호이며 출력 카테고리가 아니다.

단독 토크 / 게임 플레이 / 다인원 / 대기·자리비움

이 라벨은 콘텐츠를 나누는 기준이 아니다. 분할 기준은 사건이다(6장).

### 5.4 Long-Term Memory

수 시간짜리 방송을 자막 데이터로만 저장하지 않는다.
방송에서 발생한 사건과 의미적 관계를 저장한다.

```
예: 사건 A
    처음 언급  00:32:11
    관련 대화  01:14:22
    재언급    03:41:11
    갈등      04:21:09
    결과      05:12:44
```

시간적으로 멀리 떨어진 장면도 같은 사건으로 연결할 수 있어야 한다.
이것이 2.4(비선형 재구성)를 가능하게 하는 전제다.

5.1의 통과 결과는 독립된 조각으로 남지 않는다. 앞에서 본 내용을 누적한 상태로
뒤를 해석한다. 그래야 03:41의 발언이 00:32의 사건을 가리킨다는 것을 알아본다.

### 5.5 방송 전체의 의미 구조

```
Broadcast
├── People
├── Topics
├── Conversations
├── Situations
├── Events
├── Relationships
├── Changes
└── Temporal Links
```

고정 카테고리가 아니라 AI가 분석 중 생성·수정하는 내부 표현이다.

## 6. 핵심 시스템 3 — Autonomous Content Discovery

방송 전체를 이해한 후 다음을 판단한다.

> "이 방송에서 독립적인 콘텐츠로 만들 가치가 있는 것은 무엇인가?"

후보 개수는 정해져 있지 않다.

### 6.1 콘텐츠 후보가 보유하는 정보

핵심 내용 / 관련 인물 / 관련 사건 / 관련 장면 / 시작 지점 / 주요 변화 / 결과 /
필요한 맥락 / 다른 사건과의 관계 / 독립 콘텐츠로서의 가능성

### 6.2 분할 기준은 사건이다

하나의 영상은 하나의 사건으로 완결되어야 한다.
토크 → 게임 → 토크 → 게임으로 오가는 결과물을 만들지 않는다.
이것이 1.2에서 지적한 짜깁기다.

분할은 화면 상황(5.3)이 아니라 사건을 기준으로 한다.

- 화면이 섞여도 사건이 하나면 → 하나의 콘텐츠
- 화면이 같아도 사건이 다르면 → 다른 콘텐츠

예: 게임 중 벌어진 사건을 게임 종료 후 토크에서 계속 언급
→ 화면은 게임/토크로 섞이지만 사건은 하나 → 하나의 콘텐츠

예: 같은 게임을 3시간 연속 플레이
→ 화면은 내내 동일하지만 그 안의 사건은 여럿 → 여러 콘텐츠

콘텐츠 하나 안에서 화면 상황이 바뀌는 것은 허용된다.
단, 그 전환이 사건의 흐름상 필요한 경우에 한한다.
맥락 없이 화면만 오가는 구성은 금지한다.

### 6.3 가치 판단

모든 후보를 영상으로 만들지 않는다.

```
후보 A → 독립적으로 이해 가능 / 사건 완결 / 강한 반응 → 제작
후보 B → 재미는 있으나 결말 없음                    → 관련 사건과 결합 검토
후보 C → 맥락이 과도하게 필요                       → 제작하지 않음
후보 D → 사건은 있으나 밀도 부족                    → 제작하지 않음
```

### 6.4 참고: 후보 탐색 보조 신호

재미나이 v2가 제시한 경계 감지 아이디어는 "분할 규칙"이 아니라
"탐색 범위를 좁히는 힌트"로만 채택한다.

- 화면 상황 전환이 일정 시간 이상 유지
- 오디오 텐션이 장시간 저점 유지
- 화제 전환(임베딩 유사도 하락)

이 신호만으로 콘텐츠를 확정하지 않는다. 확정은 5.4의 사건 구조를 거친다.
각 신호의 판정 기준값은 17장에서 측정한다.

## 7. 핵심 시스템 4 — Dynamic Content Planning

콘텐츠가 선정되면 다음을 결정한다.

> "이 콘텐츠를 어떤 방식으로 보여주는 것이 가장 좋은가?"

영상 구조는 하드코딩하지 않는다.

```
콘텐츠 A: 결과 장면 → 과거 장면 → 원인 → 진행 → 결과
콘텐츠 B: 평범한 대화 → 이상한 발언 → 주변 반응 → 사실 공개 → 후속
콘텐츠 C: 게임 시작 → 실패 → 재도전 → 위기 → 성공
콘텐츠 D: 짧은 사건 → 반응 → 종료
```

콘텐츠마다 다른 구조를 사용할 수 있다.

### 7.1 YouTube Content Knowledge와의 결합

입력: 현재 방송에서 발견한 콘텐츠 + YouTube 제작 지식 → 제작 전략 생성

예: "유사 콘텐츠에서는 결과를 먼저 보여주는 방식이 자주 사용됨"

그러나 무조건 적용하지 않는다.
현재 콘텐츠의 실제 특성과 비교한 후 AI가 결정한다.

## 8. Scene Retrieval 및 Edit Planning

### 8.1 Scene Retrieval

기획을 기반으로 원본 전체에서 필요한 장면을 검색한다.

질의 예:
- "사건이 처음 언급된 장면"
- "상대방이 처음 반응한 장면"
- "상황이 바뀐 장면"
- "결과가 발생한 장면"

검색 결과 → 후보 장면 N개 → AI 검증 → 장면 선택

### 8.2 Edit Planning

AI는 영상 파일을 직접 편집하지 않고 편집 계획(JSON)을 생성한다.

```
Scene A  원본 04:31:20 ~ 04:31:42   역할: 사건의 핵심
Scene B  원본 01:12:11 ~ 01:13:04   역할: 사건의 배경
Scene C  원본 05:12:31 ~ 05:13:10   역할: 결과
```

각 장면에 편집 의도를 함께 지정한다.

자막 / 확대 / 크롭 / BGM / 효과음 / 그래픽 / 전환 / 오디오 조정 / 호흡 처리 방식(9장)

편집 계획은 렌더링과 완전히 분리된다.
계획만 보고 사람이 검토·수정할 수 있어야 한다.

## 9. 스마트 페이싱 (호흡 판단)

기계적 오디오 갭 킬링을 폐기하고 문맥적 템포 조절을 도입한다.
이 장은 재미나이 v1의 개념과 v2의 구현 형태를 흡수하되,
임계값은 전량 제거하고 판정 구조만 남긴 것이다.

### 9.1 두 종류의 정적

**[지루한 정적 → 압축 대상]**
의미 없는 마우스 클릭, 숨소리만 있는 구간, 파밍·이동 등 반복 작업, 자리비움

**[예능적 정적 → 보존 대상]**
- 황당한 상황에 직면해 말을 잇지 못하는 구간
- 반박 직전 숨을 고르는 구간
- 화자 전환 대기 구간
- 직전에 고텐션 발화(소리지름/폭소)가 있었던 직후

### 9.2 판정에 사용하는 신호

- 무음 지속 시간
- 직전 구간의 오디오 텐션
- 화자 전환 여부 및 대기 시간
- 화면상 인물의 표정·움직임 정지 여부
- 해당 컷이 편집 계획에서 부여받은 역할(8.2)

임계값을 여기에 적지 않는다.
모든 판정 기준은 설정 파일로 외부화하고 17장 절차로 결정한다.

### 9.3 호흡 처리 결과

각 컷은 다음 중 하나의 호흡 속성을 부여받는다.

```
KEEP : 정적을 그대로 보존
TRIM : 정적을 일부만 남기고 압축
CUT  : 구간 자체를 제거
```

이 값은 편집 계획 JSON과 DB(`TB_EDIT_TIMELINE.pacing_mode`)에 기록된다.

### 9.4 사람 판단과의 대조

호흡 판정은 이 시스템에서 가장 주관적인 영역이다.
따라서 자동 판정 결과를 사람이 만든 완성본과 대조하는 평가 절차(17.3)를
반드시 함께 운용한다.

## 10. 렌더링 엔진

### 10.1 역할

Phase 2~3에서 만들어진 편집 계획(JSON)만 입력받아 원본을 재단하고 자막·효과를 합성한다.
**렌더러는 어떤 판단도 하지 않는다.**

### 10.2 지원 기능

컷 / 트리밍 / 장면 순서 변경 / 크롭 / 확대 / 자막 / 그래픽 / 효과음 / BGM /
오디오 정리 / 전환 / 인코딩

### 10.3 자막

- 포맷: ASS (Advanced SubStation Alpha)
- 스타일: 고정하지 않는다. 폰트/크기/색상/애니메이션은 스타일 프로파일로 외부화하며,
  4.5의 자막 패턴 분석 결과가 프로파일을 갱신한다.

> 재미나이 v2의 고정 스타일(특정 폰트 Bold 52px, 노란색 68px 강조 등)은
> "동적 트렌드 반영" 원칙과 정면 충돌하므로 확정값에서 제외한다.
> 초기 프로파일 1종으로만 사용하고 갱신 대상으로 둔다.

> 폰트 라이선스는 임베딩·상업적 사용이 허용된 것만 채택한다.
> (예: SIL Open Font License 계열)

### 10.4 화면 연출 — 기술적 수정 사항

**[수정 1] 얼굴 추적 줌인**

재미나이 v2 표기:
`crop=w=in_w*0.83:h=in_h*0.83:x=face_center_x:y=face_center_y`

이 표현식은 그대로 동작하지 않는다.
- `face_center_x` / `face_center_y` 는 FFmpeg 내장 변수가 아니다
- `crop` 필터는 프레임마다 좌표를 자유롭게 바꾸지 못한다

대체 방안(택 1, MVP 6에서 실측 후 결정):
- (a) 줌 구간을 세그먼트로 분리하고 세그먼트별 고정 crop 적용 후 concat
  → 구현 단순, 카메라 워크가 계단식
- (b) `sendcmd` / `zoompan` 을 이용해 시간축 좌표 변화 부여
  → 부드러움 확보 가능, 필터 구성 복잡
- (c) 좌표 시퀀스를 사전 계산해 프레임 단위 처리 파이프라인에서 합성
  → 품질 최상, 처리 시간 최대

**[수정 2] 컷 연결부 오디오 처리**

재미나이 v2는 컷 연결마다 `acrossfade` 적용을 명시했으나,
`acrossfade` 는 두 입력 스트림을 이어붙일 때 쓰는 필터라
수백 개 컷 타임라인에 매 지점 적용하면 필터 그래프가 과도하게 커진다.

대체: 컷 단위 `afade` in/out(수 밀리초)으로 틱 노이즈를 제거하고,
연결은 `concat` 으로 처리한다.

**[수정 3] 오디오 정규화**

EBU R128 기반 라우드니스 정규화는 유지한다.
단 2-pass 측정 후 적용해야 구간별 편차가 생기지 않는다.

### 10.5 인코딩

H.264 / AAC, 1080p 기본, 원본이 4K인 경우 4K 옵션 제공.
YouTube 권장 규격에 맞춘 프리셋을 별도 관리한다.

## 11. 패키징 및 업로드

### 11.1 썸네일

완성본 내에서 시각적 텐션이 높은 프레임을 추출한다.

후보 선정 신호: 오디오 텐션, 표정 변화 폭, 화면 사건 발생 여부
(가중치는 17장에서 결정)

상위 N개 프레임을 고화질 이미지로 추출하여 사용자에게 제시한다.
템플릿을 고정하지 않는다.

### 11.2 메타데이터

제목 후보 3종 / 설명(타임스탬프 포함) / 태그 / 챕터

YouTube에서 분석한 패턴을 참고하되 현재 영상 내용에 맞춰 새로 생성한다.
고정 템플릿을 쓰지 않는다.

### 11.3 사람 검수 게이트 (필수 단계)

```
AI 제작 → 자동 업로드(비공개/일부공개) → 사람 검수 → 공개
```

재미나이 v2의 Zero-Touch(인간 개입 없음)는 채택하지 않는다.
검수 게이트를 통과하지 않은 영상은 공개되지 않는다.
시스템 안정화 이후 자동 공개를 선택적으로 켤 수 있게 한다.

### 11.4 YouTube Data API — 사실관계 정정

- Data API v3 기본 일일 쿼터: 10,000 units
- 영상 업로드 1건: 약 1,600 units
- 따라서 기본 쿼터로 하루 업로드 가능 수량은 약 6개 수준
- 쿼터 리셋은 태평양 시간(PT) 자정 기준

> 재미나이 v2의 "24시간 후 재시도"는 부정확하다.
> 재시도 큐는 PT 자정 리셋 시각을 기준으로 스케줄링해야 한다.

> 쿼터 증량이 필요하면 별도 신청 절차가 필요하며,
> 승인 여부와 소요 기간은 보장되지 않는다. MVP 8 착수 전 확인 항목.

## 12. 성과 피드백 및 학습 구조

### 12.1 수집 지표 (자기 채널 한정)

조회수 / 클릭률 / 평균 시청 지속 시간 / 시청자 유지율 / 이탈 구간 / 재시청 구간 /
좋아요 / 댓글 / 공유

### 12.2 제작 전략 개선

예: 특정 유형에서 초반 이탈률이 높음
→ "이 유형에서는 초반 정보 전달 방식 개선 필요"

예: 특정 장면 유형에서 유지율 상승
→ "이러한 장면 유형이 관심 유지에 긍정적일 가능성"

결과를 제작 지식에 반영한다.

### 12.3 3종 학습 루프

**A. YouTube Content Learning**
YouTube 영상 → 콘텐츠/편집/스토리 분석 → 제작 패턴 → 제작 지식

**B. Source-to-Output Learning**
원본 생방송 + 그 방송으로 만들어진 완성본
→ 어떤 장면이 선택/제거/재배치/반복/강조되었는가 → 편집 의사결정 학습

**C. Performance Learning**
완성 영상 → 실제 시청자 반응 → 성과 분석 → 전략 개선

> B가 이 시스템의 핵심 차별점이다. B가 없으면 사람이 규칙을 계속 입력하는
> 규칙 엔진에 머문다. 재미나이 v1/v2에는 B와 C가 존재하지 않는다.

## 13. 데이터 모델

### 13.1 설계 원칙

에피소드를 원본의 연속 구간 하나(`start_sec`, `end_sec`)로 저장하면
2.4(비선형 재구성)와 5.4(시간적으로 흩어진 사건 연결)이 불가능해진다.
따라서 에피소드는 시간 구간이 아니라 **"컷의 순서 있는 집합"**으로 정의한다.

### 13.2 테이블 구조

```
TB_PROJECT
  project_id (UUID, PK)
  file_path
  duration_sec
  status
  created_at

TB_EVENT                    -- Long-Term Memory (5.4)
  event_id (UUID, PK)
  project_id (FK)
  summary
  people
  relations                 -- 다른 사건과의 관계

TB_EVENT_MENTION            -- 하나의 사건이 갖는 흩어진 시점들
  mention_id (BIGINT, PK)
  event_id (FK)
  source_start_sec
  source_end_sec
  role                      -- 최초언급 / 관련대화 / 재언급 / 갈등 / 결과 등

TB_CONTENT_CANDIDATE        -- 콘텐츠 발견 결과 (6장)
  candidate_id (UUID, PK)
  project_id (FK)
  core_summary
  related_event_ids

  render_status
  ※ start_sec / end_sec 컬럼을 두지 않는다

TB_EDIT_TIMELINE            -- 비선형 재구성의 핵심
  cut_id (BIGINT, PK)
  episode_id (FK)

  source_start_sec          -- 원본에서의 위치 (순서 무관)

  subtitle_ref

TB_YT_REFERENCE             -- 레퍼런스 학습 (12.3 A)
  ref_id (UUID, PK)
  video_id
  public_metrics            -- 공개 지표만
  extracted_patterns (JSON)
  ※ 원본 미디어는 저장하지 않는다 (4.6)

TB_SOURCE_OUTPUT_PAIR       -- 원본↔완성본 학습 (12.3 B)

  source_ref
  output_ref
  selection_analysis (JSON)

TB_PERFORMANCE              -- 성과 학습 (12.3 C)
  perf_id (UUID, PK)
  episode_id (FK)
  metrics (JSON)
  collected_at

TB_CALIBRATION_PROFILE      -- 17장
  profile_id (UUID, PK)

  params (JSON)

  eval_score
```

## 14. 파이프라인 상태 전이도

```
QUEUED
  → PARSING          (음성/영상/오디오 멀티모달 추출)
  → UNDERSTANDING    (사건·인물·관계 구조 생성)
  → DISCOVERING      (콘텐츠 후보 발견)
  → EVALUATING       (가치 판단 / 제작 여부 결정)
  → PLANNING         (구조 결정 + 장면 검색 + 호흡 설계)
  → RENDERING
  → PACKAGED
  → REVIEW_PENDING   (사람 검수 대기)  ← 필수 게이트
  → PUBLISHED
```

분기 상태:
- `NO_CONTENT` (제작 가치 있는 콘텐츠 없음 — 정상 종료)
- `FAILED` (실패, 사유 기록)
- `RETRY_QUEUED` (업로드 쿼터 초과 등)

## 17. 캘리브레이션 절차 (임계값 대체)

재미나이 v2가 제시한 숫자들(-40dB, 0.3초, 텐션 0.7, 코사인 0.45, 이동평균 0.15,
가중치 0.6/0.4 등)은 근거 데이터가 제시되지 않았다.
이 값들이 틀리면 시스템 전체가 오작동하므로 확정값으로 넣지 않는다.
대신 아래 절차로 측정하여 결정한다.

### 17.1 파라미터 외부화

모든 판정 기준을 코드가 아닌 설정 파일에 둔다.

대상: 무음 판정 레벨, 무음 최소 지속 시간, 텐션 계산 가중치, 텐션 고저 기준,
화면 상황 판정 기준, 화제 전환 판정 기준, 보조 신호 조합 조건,
썸네일 점수 가중치, **1차 통과 밀도**, **2차 정밀 통과 대상 선정 기준**

설정 파일은 채널 단위 프로파일로 저장한다(`TB_CALIBRATION_PROFILE`).
채널·장르·마이크 환경이 다르면 값도 달라진다.

### 17.2 측정용 데이터셋 구축

- (a) 본인 방송 원본 수 시간 분량
- (b) 그 원본으로 사람이 실제 편집한 완성본
- (c) (a)와 (b)의 구간 대응 관계 라벨

(b)가 그대로 12.3 B(Source-to-Output Learning)의 학습 데이터가 된다.
따라서 이 작업은 캘리브레이션과 학습에 이중으로 쓰인다.

### 17.3 평가 지표

- **호흡 판정 정확도**
  - 사람이 보존한 정적을 시스템도 보존했는가 (재현율)
  - 사람이 자른 정적을 시스템도 잘랐는가 (정밀도)
- **콘텐츠 발견 일치도** — 사람이 콘텐츠로 인정할 만한 구간을 시스템이 찾아냈는가
- **오탐 비율** — 사람이 버릴 구간을 콘텐츠로 올렸는가

### 17.4 튜닝 절차

1. 초기값을 데이터셋에서 실측(예: 방송 환경의 실제 무음 레벨 분포)
2. 파라미터 스윕 후 17.3 지표로 평가
3. 지표가 가장 높은 조합을 채널 프로파일로 저장
4. 방송 환경 변경(마이크·게임·합방 여부) 시 재측정

### 17.5 원칙

**측정하지 않은 값은 문서에 확정값으로 적지 않는다.**
초기 개발 중 임시값을 쓰더라도 반드시 "임시" 표기를 유지한다.

## 19. MVP 로드맵

착수 순서는 ai편집.txt의 MVP 순서를 그대로 따른다.
각 MVP는 성공 기준을 통과해야 다음으로 넘어간다.

**MVP 1 — YouTube Content Intelligence**
- 목표: YouTube 영상이 어떻게 만들어지는지 AI가 분석 가능한지 검증
- 입력: 관련 분야 영상 데이터셋
- 출력: 영상 구조 / 편집 패턴 / 스토리 패턴 / 장면 선택 패턴 / 제목·썸네일 관계
- 성공 기준: 사람이 봤을 때 분석 결과가 실제 영상의 제작 의도와 일치한다고
  판단되는 비율 확보
- 선행 확인: 4.6 데이터 취급 정책 확정

**MVP 2 — Broadcast Understanding**
- 입력: 4~6시간 생방송 1편
- 출력: 방송 의미 구조 / 사건 / 인물 / 대화 / 관계 / 시간적 연결
- 성공 기준: 사람이 기억하는 주요 사건을 누락 없이 잡아내는가
- 포함: 5장 전체(1차 전 구간 통과 + 2차 정밀 통과), 상황 라벨, 사건 그래프
- 실측 항목: 1차 통과 밀도별 사건 검출률과 처리 시간

**MVP 3 — Content Discovery**
- 출력: 방송에서 발견한 콘텐츠 후보
- 성공 기준(1차 검증 — 이 프로젝트의 첫 관문):

```
6시간 생방송 입력
  ↓ AI 전체 분석
  ↓ 콘텐츠 후보 생성
  ↓ 사람이 실제 방송을 직접 확인
  ↓ AI가 발견한 콘텐츠와 사람이 발견할 콘텐츠의 일치도 평가

항목별 평가:
  - 관련 장면을 제대로 찾는가
  - 서로 다른 시간대의 장면을 연결하는가
  - 사건의 시작과 결과를 이해하는가
  - 불필요한 장면을 제외하는가
```

> 이 단계까지는 영상을 만들지 않는다.
> 여기서 실패하면 뒤 단계를 만들어도 의미가 없다.

**MVP 4 — Source-to-Output Mapping**
- 입력: 원본 생방송 + 그 방송으로 만든 완성본
- 출력: 어떤 장면이 선택/제거/재배치되었는지 분석
- 겸용: 17.2 캘리브레이션 데이터셋 구축과 동일 작업

**MVP 5 — Dynamic Planning**
- AI가 콘텐츠마다 영상 구조를 스스로 결정
- 포함: 7장, 8장(Scene Retrieval + Edit Planning), 9장(호흡 설계)
- 출력: 편집 계획 JSON (렌더링 없음)
- 성공 기준: 편집 계획만 읽고도 사람이 결과물을 예상할 수 있는가

**MVP 6 — Automatic Editing**
- 편집 계획을 실제 영상으로 렌더링
- 포함: 10장 전체, 10.4 기술 대체안 실측 후 확정

**MVP 7 — YouTube Packaging**
- 제목 / 썸네일 / 설명 / 챕터

**MVP 8 — Automatic Upload**
- YouTube API 연동 + 검수 게이트(11.3)
- 선행 확인: 11.4 쿼터 정책

**MVP 9 — Performance Learning**
- 성과 데이터 수집 및 제작 전략 개선

## 20. 기술 스택 및 사전 준비 항목

### 20.1 스택

```
앱 래퍼   : PyQt6 또는 Electron (PC 단일 실행형)
코어      : Python 3.10+
음성      : WhisperX 등 단어 단위 타임스탬프 지원 STT
화자 분리 : pyannote 계열
비전      : OpenCV + 얼굴/장면 검출
오디오 분석: Librosa, Soundfile
영상 처리 : FFmpeg CLI
자막      : ASS, Pillow
DB        : SQLite(단일 PC) → 필요 시 PostgreSQL
```

### 20.2 사전 준비 항목 (착수 전 확인 필요)

- 화자 분리 모델은 HuggingFace 게이트 모델 접근 승인이 필요하다.
  승인 절차와 라이선스 조건을 MVP 2 착수 전에 확인한다.
- 자막 폰트의 임베딩·상업 사용 허용 여부 확인
- YouTube Data API 프로젝트 생성 및 쿼터 확인 (MVP 8 이전)
- 레퍼런스 영상 데이터 취급 정책 확정 (MVP 1 이전)
- GPU 사양 확정: 6시간 원본의 STT + 비전 분석 처리 시간 실측

### 20.3 일정에 관하여

재미나이 v2의 6주 일정은 채택하지 않는다.
STT·화자분리·게임 화면 인식·렌더러·GUI·API 연동을 6주에 묶는 것은
근거가 제시되지 않은 낙관이다.

일정은 MVP 3(1차 검증)의 결과를 본 뒤 산정한다.
MVP 1~3까지의 소요를 실측한 다음 나머지를 추정하는 방식으로 간다.

## 21. 리스크 및 미해결 과제

- **R1. MVP 3 실패 가능성** — "방송에서 콘텐츠를 발견하는 것" 자체가 이 프로젝트의
  난이도 대부분을 차지한다. 여기서 사람 판단과의 일치도가 낮으면 계획을 재설계해야 한다.
- **R2. 게임 화면 인식 범위** — 게임 종류마다 UI가 달라 일반화가 어렵다.
  초기에는 실제 플레이하는 게임 소수로 한정한다.
- **R3. 처리 시간** — 6시간 원본을 1차 전 구간 통과 + 2차 정밀 통과로 처리하는 시간이
  실사용 가능한 수준인지 미검증. MVP 2에서 실측한다.
  1차 통과 밀도가 비용과 시간을 결정하는 핵심 변수다.
- **R4. 학습 데이터 부족** — 12.3 B는 원본+완성본 쌍이 필요한데 수량 확보가 관건이다.
  본인 방송 아카이브가 사실상 유일한 소스가 될 가능성이 높다.
- **R5. 레퍼런스 수집의 약관·저작권 리스크** — 4.6 정책으로 완화하되 완전히 해소되지는 않는다.
- **R6. 호흡 판정의 주관성** — 사람마다 정답이 다르다.
  채널 프로파일 단위로만 최적화 가능하다.

3. 에피소드별 썸네일 후보 이미지 (PNG/JPG)
4. 에피소드별 메타데이터 패키지 (제목 후보 3종, 설명, 태그, 챕터 / JSON·TXT)
5. 에피소드별 편집 계획 (JSON) — 사람이 검토·수정 가능
6. 작업 리포트 (발견 후보 수, 제작 결정 수, 제외 사유, 처리 시간)
7. 채널 캘리브레이션 프로파일

## 23. 핵심 철학

사람이 AI에게 "이런 구조로 만들어라"라고 계속 규칙을 입력하는 시스템이 아니다.

실제 YouTube 콘텐츠를 분석하여 "좋은 콘텐츠가 실제로 어떻게 만들어지고 있는가"를
학습하고, 새로운 생방송을 분석하여 "이 방송에서는 무엇을 만들어야 하는가"를
AI가 판단하며, "이 콘텐츠는 어떻게 만들어야 하는가"까지 AI가 결정하는 시스템을 만든다.

고정된 템플릿을 사용하는 AI가 아니라 **상황에 따라 판단하는 AI 콘텐츠 프로듀서**를
만드는 것이 본 프로젝트의 지향점이다.
